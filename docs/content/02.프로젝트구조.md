# QuantTrader 프로젝트 구조

이 문서는 [01.프로젝트회고](E:/projects/QuantTrader/src/QuantTrader/Docs/01.프로젝트회고.md)에서 정리한 배경을 바탕으로, 현재 QuantTrader를 어떤 구조로 가져가려는지 설명한다.  
회고 문서가 "왜 이런 구조가 되었는가"를 다뤘다면, 이 문서는 "그래서 지금 무엇을 어디에 둘 것인가"를 정리하는 문서다.

## 1. 구조의 기본 원칙

현재 구조는 하나의 큰 프로그램 안에 모든 기능을 욱여넣지 않는다.  
역할이 다른 것들은 실행 단위부터 분리한다.

핵심 원칙은 다음과 같다.

- 데이터 수집과 전략 검증은 분리한다.
- 전략 규칙과 전략 실행은 분리한다.
- 전략 검증과 실주문 집행은 분리한다.
- 공통 데이터 형식은 별도 프로젝트에서 관리한다.
- UI는 핵심 규칙보다 뒤에 둔다.

즉 구조의 중심은 "기능 나열"이 아니라 "책임 분리"다.

## 2. 현재 프로젝트 구성

현재 기준으로 프로젝트는 다음과 같이 정리한다.

```text
src/
  QuantTrader.Collector/
  QuantTrader.Contracts/
  QuantTrader.Researcher/
  QuantTrader.Strategies/
  QuantTrader.Trader/
  QuantTrader.WebUI/
```

각 프로젝트의 역할은 다음처럼 구분한다.

- `QuantTrader.Collector` (1차완료)
  - 시장 데이터를 수집해서 PostgreSQL에 적재한다.
- `QuantTrader.Contracts`
  - 프로젝트 간 공통 요청/응답 형식을 정의한다.
- `QuantTrader.Strategies`
  - 전략 규칙만 정의한다.
- `QuantTrader.Researcher`
  - 과거 데이터 기준 전략 검증과 백테스트를 담당한다.
- `QuantTrader.Trader`
  - 활성 전략을 실제 시장에 집행한다.
- `QuantTrader.WebUI`(추후구현)
  - 사용자 화면을 담당한다.

## 3. 왜 이렇게 나누는가

### Collector

Collector는 데이터 공급자다.  
시장 데이터를 가져와 DB에 넣는 것이 전부다.

Collector가 하지 말아야 하는 것:

- 전략 판단
- 백테스트
- 주문 실행

즉 Collector는 "데이터를 쌓는 봇"이다.

### Strategies

Strategies는 전략 규칙의 집합이다.  
여기에는 ORB 같은 전략이 들어간다.

전략은 최소한 다음 네 가지를 가져야 한다.

1. 대상주 선정
2. 매수 시점
3. 손절 시점
4. 익절 시점

여기에 필요한 경우 다음이 추가된다.

- 시간 종료 청산
- 거래량 조건
- 리스크 규칙
- 수량 산정

중요한 점은, Strategies는 규칙만 가져야 한다는 것이다.

즉 포함하지 않는 것은 다음과 같다.

- DB 조회
- 주문 API 호출
- 백테스트 루프
- 실시간 실행 루프

### Researcher

Researcher는 전략을 검증하는 프로젝트다.  
과거 분봉을 읽고, 전략을 실행하고, 그 결과를 집계한다.

여기서 중요한 건 Researcher가 전략을 새로 정의하는 것이 아니라,  
이미 정의된 전략과 파라미터 조합을 실험하는 주체라는 점이다.

Researcher가 하는 일:

- 과거 분봉 조회
- 전략 파라미터 조합 실행
- 가상 주문/가상 체결
- 손익, 승률, MDD 계산
- 결과 저장과 조회

즉 Researcher는 "연구와 검증의 실행기"다.

### Trader

Trader는 실주문 집행기다.  
이미 ON 된 전략과 파라미터를 읽고, 실제 주문을 넣는다.

Trader가 하는 일:

- 활성 전략 로드
- 당일 분봉 기준 실행
- 주문 의도 생성
- 실제 주문 API 호출
- 체결/미체결/포지션 관리

즉 Trader는 "연구"를 하지 않는다.  
선택된 전략을 실제로 실행할 뿐이다.

### Contracts

Contracts는 프로젝트 간 공통 형식을 정의한다.  
실제 통신을 하는 프로젝트는 아니지만, 서로 같은 형식으로 말하게 만드는 역할을 한다.

예를 들어:

- 백테스트 요청 DTO
- 백테스트 결과 DTO
- 주문 의도 모델
- 공통 enum

즉 Contracts는 "공통 서류 양식"이다.

### WebUI

WebUI는 사용자와 시스템이 만나는 지점이다.  
지금은 후순위다.  
전략과 백엔드 구조가 충분히 정리된 뒤 다시 손볼 수 있다.

## 4. Strategies 내부 구조

전략은 프로젝트를 전략별로 쪼개지 않고, `QuantTrader.Strategies` 하나 안에서 폴더로 나눈다.

예를 들어 ORB는 이렇게 가져간다.

```text
QuantTrader.Strategies/
  Abstractions/
  Orb/
    Filters/
    Entry/
    Exit/
    Risk/
```

이 구조를 쓰는 이유는 단순하다.

- 전략 수가 아직 많지 않다.
- 전략별로 프로젝트를 쪼개면 오히려 무거워진다.
- 공통 추상화와 상태 타입이 많아서 결국 다시 얽힌다.

즉 지금은:

- 프로젝트는 하나
- 전략별 폴더 분리

가 가장 적절하다.

## 5. Researcher와 Trader의 실행 구조

현재 정리된 방향에서 전략은 같은 프로젝트를 공유하지만, 실행 방식은 다르다.

### Researcher

- 과거 분봉을 읽는다.
- `ResearcherEngine`으로 전략을 실행한다.
- 가상 체결을 한다.
- 결과를 비교한다.

### Trader

- 당일 분봉을 읽는다.
- `TraderEngine`으로 전략을 실행한다.
- 실제 주문을 넣는다.
- 포지션과 체결을 관리한다.

즉 둘은 같은 전략 정의를 공유하지만, 같은 파라미터를 공유하는 것은 아니다.

- Researcher는 여러 파라미터를 테스트한다.
- Trader는 선택된 하나의 파라미터 세트만 실행한다.

이 구조 덕분에 전략 코드와 전략 운영 파라미터를 분리해서 다룰 수 있다.

## 6. 데이터와 설정 위치

코드는 `src/` 아래에 둔다.  
런타임 데이터는 코드와 분리한다.

즉:

- `src/`
  - 프로젝트 코드
- `data/`
  - 캐시, 마스터 파일, 런타임 산출물

설정은 각 프로젝트 내부에 둔다.

예:

- `QuantTrader.Collector`
  - `.env`, `.env.example`
- `QuantTrader.Researcher`
  - `appsettings.json`
  - `appsettings.Development.json`
- `QuantTrader.Trader`
  - `appsettings.json`
  - `appsettings.Development.json`
- `QuantTrader.WebUI`
  - `.env`, `.env.example`

즉 설정은 프로젝트 소유로 두고, 루트 공용 `configs/`는 현재 두지 않는다.

## 7. 현재 우선순위

현재 우선순위는 아래와 같다.

1. `QuantTrader.Strategies`
2. `QuantTrader.Researcher`
3. `QuantTrader.Trader`

`QuantTrader.WebUI`는 뒤로 둔다.  
전략과 백엔드 구조가 먼저 안정되어야 화면도 덜 흔들리기 때문이다.

## 마무리

현재 구조는 완성형이 아니라, 책임을 명확히 나누기 위한 시작점이다.  
중요한 건 "프로젝트를 많이 만드는 것"이 아니라, 각 프로젝트가 무엇을 책임지고 무엇을 책임지지 않는지 분명히 하는 것이다.

지금 기준에서 QuantTrader는 다음 한 줄로 요약할 수 있다.

> Collector는 데이터를 쌓고, Strategies는 규칙을 정의하고, Researcher는 검증하고, Trader는 집행한다.
