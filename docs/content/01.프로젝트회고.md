# QuantTrader 프로젝트 회고

이 문서는 QuantTrader를 처음 고민하던 시점부터, ORB 전략을 중심으로 현재 구조를 정리하기까지의 과정을 블로그 글처럼 풀어쓴 기록이다.  
처음에는 단순히 "백테스트 프로그램을 하나 만들자"는 생각에서 출발했지만, 실제로는 기술 선택, 데이터 저장 방식, 전략 책임 분리, 수집기와 실행기의 경계까지 계속 다시 정의해야 했다.

## 1. 시작은 단순한 백테스트 프로그램이었다

출발점은 분명했다.  
나는 ORB 전략을 검증하고 싶었고, 이를 위해 과거 데이터를 돌려볼 수 있는 백테스트 프로그램이 필요했다.

처음에는 전략 로직 하나를 빨리 확인할 수 있는 구조를 상상했다. 하지만 곧 문제가 보였다.

- 문서와 코드가 한 덩어리로 섞이면 관리가 어렵다.
- 전략 연구용 기능과 나중의 실거래 기능은 관심사가 다르다.
- 백테스트를 위한 데이터 구조와 실제 운영 구조는 처음부터 분리해서 생각해야 한다.

이 시점부터 프로젝트는 "백테스트 프로그램"이 아니라 "전략 연구와 실행을 분리한 시스템"으로 바뀌기 시작했다.

## 2. 아키텍처를 먼저 고정하지 않기로 했다

초기에는 구조를 너무 빨리 확정하려는 유혹이 있었다.  
하지만 실제로는 전략 자체도 아직 흔들리고 있었고, 필터 기준도 명확하지 않았다.

그래서 한 가지 원칙을 먼저 세웠다.

> 최종 구조를 너무 일찍 만들지 말고, 지금 당장 필요한 관심사를 먼저 분리하자.

그 결과 처음 정리된 큰 축은 다음과 같았다.

- 연구용 백엔드
- 웹 UI
- 데이터 수집기

즉, "한 개의 거대한 프로그램"이 아니라, 역할별로 분리된 실행 단위로 보기 시작했다.

## 3. Python과 C# 사이에서 방향을 잡다

중간에 가장 오래 고민한 것 중 하나는 백엔드 스택이었다.

- Python + FastAPI + React
- C# + ASP.NET Core + React

처음에는 백테스트와 데이터 가공 속도 때문에 Python이 자연스럽게 보였다. 실제로도 초기 연구 단계에서는 Python이 더 빠르게 움직였다.  
필터를 추가하고, 조건을 바꾸고, 과거 데이터를 다시 돌리는 과정은 Python 쪽이 훨씬 민첩했다.

하지만 프로젝트가 커질수록 또 다른 현실이 보였다.

- 실거래 엔진은 안정성이 중요하다.
- 장시간 실행, 상태 관리, 주문 흐름은 C#이 더 편하다.
- 나중에 NAS나 운영 환경으로 옮길 때도 .NET 쪽이 구조화하기 쉽다.

그래서 최종적으로는 이렇게 정리했다.

- Python: 데이터 수집기
- C#: 연구용 본체와 실거래 본체

즉 Python은 "수집", C#은 "분석과 실행"으로 역할이 갈라졌다.

## 4. ORB 전략을 기준으로 생각을 다시 정리했다

이 프로젝트가 진짜 정리되기 시작한 계기는 ORB 전략을 다시 정의하면서였다.

처음에는 ORB를 "시가 이후 몇 분 동안의 범위를 보고 돌파를 찾는 전략" 정도로 가볍게 생각했다.  
그런데 실제로 백테스트와 실거래 구조를 만들려면, 전략은 단순 진입 조건만으로 끝나지 않는다는 점이 명확해졌다.

전략은 최소한 다음 네 가지를 전부 가져야 했다.

1. 대상주 선정
2. 매수 시점
3. 손절 시점
4. 익절 시점

그리고 그 위에 부가적으로 붙는 것들이 있었다.

- 시간 종료 규칙
- 거래량 조건
- 갭상승 범위
- 리스크 규칙
- 수량 산정 방식

즉 ORB는 단순한 "돌파 감지기"가 아니라, A부터 Z까지 완결된 규칙 집합이어야 했다.

## 5. 대상주 선정 기준을 먼저 정리했다

전략을 실제로 돌리려면 전종목을 매번 같은 비중으로 볼 수는 없었다.  
그래서 가장 먼저 정리된 1차 필터가 갭상승이었다.

초기 논의 끝에 1차 백테스트 구간은 다음처럼 잡았다.

- 5% ~ 10%
- 10% ~ 15%
- 15% 이상

여기서 중요한 건 "갭상승 여부" 자체보다, 갭의 정도를 범위 파라미터로 봐야 한다는 점이었다.

5% 갭과 20% 갭은 같은 집단이 아니다.

- 수급 구조가 다르고
- 뉴스/테마 개입 가능성이 다르고
- 유지력과 되밀림 리스크도 다르다

즉 갭상승 필터는 단일 값이 아니라 `min_gap_pct`, `max_gap_pct` 형태의 범위 파라미터가 되어야 했다.

그 다음으로 붙인 필터는 오프닝 거래량이었다.

기준은 절대 거래량이 아니라, 최근 20거래일 동일 시간 구간 대비 비율이다.

예를 들어 5분 ORB를 쓴다면:

- 오늘 09:00~09:05 거래량
- 최근 20거래일의 09:00~09:05 평균 거래량

을 비교해서 비율을 구한다.

초기 비교 구간은 다음처럼 잡았다.

- 1.5배 ~ 2.0배
- 2.0배 ~ 3.0배
- 3.0배 ~ 5.0배
- 5.0배 이상

## 6. 데이터 구조를 고민하다가, "무엇을 저장해야 하는가"가 핵심이라는 걸 깨달았다

초기에는 전종목 틱데이터를 다 저장할지, 분봉을 저장할지, 둘을 한 테이블에 넣을지 같은 고민을 많이 했다.

정리된 결론은 이렇다.

- 틱과 분봉은 같은 테이블에 넣지 않는다.
- 틱은 원천 데이터, 분봉은 집계 데이터다.
- 갭상승 판단은 별도의 장 시작 기준값 테이블이 필요하다.

그 과정에서 `market_open_snapshot`이라는 개념이 나왔다.

이 테이블은 다음 값들을 가진다.

- 전일 종가
- 당일 시가
- 갭상승률

즉 전일 대비 갭상승 여부는 분봉 전체를 읽지 않아도 이 테이블만으로 바로 판단할 수 있게 되었다.  
이 발견은 중요했다. 처음엔 전종목 분봉을 먼저 봐야 할 것처럼 생각했지만, 실제로는 장 시작 스냅샷만으로 1차 후보군을 크게 줄일 수 있었다.

## 7. DuckDB에서 PostgreSQL로 넘어간 이유

처음 저장소는 DuckDB를 고려했다.  
읽기 성능이 좋고, 로컬 단일 연구 환경에서는 훌륭한 선택이었다.

하지만 프로젝트가 커질수록 DuckDB의 장점보다 한계가 더 크게 보이기 시작했다.

- 다른 프로세스와 동시 접근이 불편하다.
- DBeaver 같은 도구로 열어두면 충돌이 난다.
- 나중에 NAS로 옮기고 싶다.
- C# 중심으로 프로젝트를 키울수록 PostgreSQL 쪽이 더 자연스럽다.

결정적으로, 내가 예전에 DB 마이그레이션에서 스트레스를 크게 받았기 때문에 "언젠가 PostgreSQL로 갈 것"이 거의 확실했다.  
그렇다면 가장 싼 비용으로 옮길 수 있는 시점인 지금 바꾸는 게 맞았다.

결국 저장소는 PostgreSQL로 바뀌었고, 분봉 테이블은 월별 파티셔닝을 적용하는 방향으로 정리되었다.  
이유는 단순했다. 하루에 수십만 행이 쌓이고, 1년이면 수억 행이 될 수 있기 때문이다.

## 8. 한국투자증권 API를 실제로 붙이면서 현실을 배웠다

문서만 볼 때와 실제로 붙일 때는 완전히 달랐다.

확인된 사실은 대략 이랬다.

- 당일 체결 API는 과거 일자 조회용이 아니다.
- 과거 분봉 API는 종목별 개별 호출 구조다.
- 하루치 1분봉도 보통 여러 번 요청해야 다 모인다.
- 전종목 백필은 결국 느릴 수밖에 없다.

여기에 유량 제한까지 있었다.

- worker를 너무 올리면 `초당 거래건수 초과`가 발생한다.
- 응답 1회에 들어오는 분봉 수는 대략 120건 수준으로 보인다.
- 하루 1종목이 아니라 "한 종목의 하루치"도 여러 호출로 나뉜다.

즉 성능 병목은 DB보다 브로커 API였다.

이 과정에서 다음과 같은 개선이 들어갔다.

- 토큰 캐시 파일 저장
- 종목 단위 저장
- 중간 실패 후 이어받기
- worker 수 조정
- 요청 간 delay/stagger
- 잘못된 종목 코드 필터링

결과적으로, 전종목 단위 백필도 완전 불가능한 수준은 아니게 만들었다.

## 9. 현재 구조는 "수집기"와 "본체"를 분리하는 방향으로 정리되었다

지금 기준으로 프로젝트는 다음 역할로 나뉜다.

- `QuantTrader.Collector`
  - 한국투자증권 API 호출
  - 장중/장마감 데이터 적재
  - PostgreSQL 저장

- `QuantTrader.Strategies`
  - 전략 규칙 정의
  - ORB 포함 각 전략의 필터/진입/청산/리스크

- `QuantTrader.Researcher`
  - 과거 분봉 기반 전략 검증
  - 백테스트
  - 파라미터 조합 비교
  - 결과 저장/조회

- `QuantTrader.Trader`
  - 활성 전략 실행
  - 주문 API 호출
  - 체결/포지션 관리

- `QuantTrader.Contracts`
  - 공통 DTO와 계약 모델

- `QuantTrader.WebUI`
  - 결과 확인과 파라미터 입력용 UI

여기서 중요한 정리는 이것이다.

전략은 `Strategies`에 있고,  
`Researcher`는 전략을 검증하고,  
`Trader`는 그 전략을 실제로 집행한다.

## 10. 전략 실행을 어떻게 나눌 것인가에 대한 고민

가장 오래 헷갈렸던 부분은 `Researcher`, `Trader`, `Engine`의 경계였다.

처음에는 별도의 `Engine` 프로젝트를 두는 방안도 떠올랐다.  
하지만 그 구조는 오히려 전략과 실행, 연구와 집행의 책임을 흐리게 만들었다.

정리된 결론은 다음과 같다.

- 전략 프로젝트는 규칙만 가진다.
- `Researcher`는 자기 안에서 `ResearcherEngine`으로 전략을 실행한다.
- `Trader`는 자기 안에서 `TraderEngine`으로 전략을 실행한다.
- 같은 전략 정의를 공유하지만, 파라미터 값은 다를 수 있다.

즉:

- `Researcher`
  - 여러 파라미터 조합을 돌려본다.
- `Trader`
  - ON 된 전략과 선택된 파라미터 하나를 실행한다.

전략 코드와 전략 파라미터를 분리해서 보니, 그동안 꼬였던 개념이 정리되었다.

## 11. 결국 이 프로젝트가 지향하는 것은 무엇인가

지금 시점의 QuantTrader는 단순한 백테스트 프로그램이 아니다.

이 프로젝트는 다음 세 가지를 동시에 만족하려는 방향으로 가고 있다.

1. 전략을 과거 데이터로 검증할 수 있어야 한다.
2. 같은 전략을 실시간 데이터에도 적용할 수 있어야 한다.
3. 데이터 수집, 전략 정의, 검증, 집행의 책임이 섞이지 않아야 한다.

즉 핵심은 "전략을 코드로 정의하고, 같은 전략을 연구와 실전에서 일관되게 재사용하는 것"이다.

## 마무리

처음에는 ORB 하나만 빨리 돌려보고 싶었다.  
그런데 실제로 프로젝트를 쌓아가다 보니, 더 중요한 건 "이 전략을 어떤 구조에서 오래 가져갈 것인가"였다.

지금까지 정리한 결과, 가장 중요한 원칙은 다음처럼 요약된다.

- 데이터 수집은 수집기에게 맡긴다.
- 전략 규칙은 전략 프로젝트에만 둔다.
- 과거 검증은 Researcher가 맡는다.
- 실제 주문 집행은 Trader가 맡는다.
- 그리고 이 모든 과정은 미래 데이터를 보지 않는 1분봉 단위 흐름 위에서 돌아가야 한다.

아직 갈 길은 멀다.  
하지만 적어도 이제는, 이 프로젝트가 어디로 가야 하는지는 처음보다 훨씬 분명해졌다.
