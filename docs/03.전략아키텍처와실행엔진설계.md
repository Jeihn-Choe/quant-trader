# 03. 전략 아키텍처와 실행 엔진 설계

작성일: 2026-03-14

## 1. 전략은 "의도"만을 내놓아야 한다

처음 구조를 잡을 때 가장 헷갈렸던 부분은 "전략이 어디까지 책임져야 하는가"였다.  
단순히 생각하면 전략이 주문까지 내면 편할 것 같지만, 실제 주식 트레이딩 봇의 세계는 그렇게 단순하지 않았다.

전략이 주문 집행과 계좌 관리까지 직접 개입하기 시작하면, 백테스트와 실거래 코드가 달라지고 관리 비용이 기하급수적으로 늘어난다. 그래서 우리는 명확한 선을 그었다.

> **전략은 "의도(Intent)"를 생성하고, 실행기(Trader)는 "집행(Execution)"을 담당한다.**

이 결정 덕분에 전략은 호가가 비었는지, 내 계좌 잔고가 얼마인지 신경 쓰지 않고 오직 "어떤 상황에 사야 하는가"라는 도메인 로직에만 집중할 수 있게 되었다.

## 2. Contracts: 시스템의 공통 언어

프로젝트가 늘어날수록 서로 다른 언어로 말하는 것이 가장 큰 위협이었다.  
우리는 `QuantTrader.Contracts`를 단순한 모델 모음집이 아니라, 시스템 전체를 관통하는 **"공통 서류 양식"**으로 정의했다.

특히 다음 두 가지 모델이 핵심 고리 역할을 한다.

- **`TradingIntent`**: 전략이 실행기에게 전달하는 논리적 결정 사항. (비중, 참조가 등)
- **`Position`**: 실행기가 전략에게 알려주는 현재 보유 상태. (진입가, 수량 등)

이 고리가 완성되면서, 전략 프로젝트(`Strategies`)는 실행기(`Trader`)가 누구인지 몰라도 `Contracts` 모델만 보고 판정을 내릴 수 있는 독립성을 얻었다.

## 3. 로직은 하나, 파라미터는 무한대

ORB 전략을 코드로 옮기면서 가장 중요하게 생각한 것은 "유연성"이다.  
"5분봉 ORB가 정답이다"라고 못 박는 대신, **"파라미터 주입형 구조"**를 선택했다.

- `IStrategy.Initialize(IStrategyParameter)`

이 구조 덕분에 `Researcher`는 수만 개의 파라미터 조합을 초고속으로 탐색(Backtest)할 수 있고, `Trader`는 그중 검증된 단 하나의 파라미터 세트를 실시간으로 집행(Live)할 수 있다. 로직은 단 한 줄도 고칠 필요 없이 말이다.

## 4. 실행 엔진(Runner)의 배치

전략 실행 엔진을 어디에 둘 것인가에 대해서도 깊은 논의가 있었다.  
결론은 **"엔진은 각 실행 주체(Researcher, Trader) 내부의 Infrastructure 레이어에 존재한다"**는 것이다.

- **Researcher Engine**: 과거 데이터를 DB에서 긁어와 고속으로 루프를 돌리는 시간 가속기.
- **Trader Engine**: 실시간 데이터 이벤트를 대기하다가 전략을 깨우는 이벤트 리스너.

전략은 그저 엔진이 불러주기를 기다리는 "순수 함수 묶음"으로 존재한다. 이 분리를 통해 우리는 전략 코드의 오염 없이 다양한 실행 환경을 지원할 수 있게 되었다.

## 5. 데이터 가독성과 정밀도

퀀트 시스템에서 데이터는 생명이다.  
단순히 필드만 나열하는 것이 아니라, 각 필드 위에 상세한 XML 주석을 달아 인텔리센스 지원을 극대화했다. `readonly record struct`를 사용하여 대량 데이터 처리 시의 성능(Memory Allocation 최소화)까지 챙겼다.

- `MinuteBar`: 시고저종과 거래량의 명확한 정의.
- `MarketOpenSnapshot`: 갭 필터링의 기준이 되는 시가 정보.

## 마무리

이제 구조는 충분히 단단해졌다.  
데이터는 `Contracts`를 통해 흐르고, 전략은 `Strategies`에서 규칙을 정의하며, 엔진은 각자의 환경에서 전략을 실행한다.

이 구조는 단순히 ORB 하나를 돌리기 위한 것이 아니다.  
앞으로 추가될 수많은 전략과 복잡한 매매 기법들을 수용할 수 있는 **"진짜 주식 트레이딩 시스템"**의 기반이다. 이제 이 튼튼한 뼈대 위에 ORB의 구체적인 살점을 붙일 차례다.
